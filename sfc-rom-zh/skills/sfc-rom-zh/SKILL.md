# 把 SFC ROM 繁中化

從兩個做完的專案萃出來：Chrono Trigger 和 Bahamut Lagoon。這裡寫的是方法，不是位址。
新 ROM 的每一個位址都不一樣，`reference/chrono-trigger.md` 記錄 CT 的答案，
只是當作「一個答案長什麼樣」的範例。

CT 最貴的三個錯誤都是同一個錯誤：**相信了一件沒有辦法被證偽的事**。
字模「顯然」是 8x12（實際是 12x12 分兩塊）。某個位元組樣式「顯然」是讀那張表的程式
（12 個命中全是無關指令裡的巧合）。壓縮器「顯然」能用因為它通過了自己解碼器的 round-trip
（實機當機）。

**有經驗會讓這個風險變高，不是變低**，因為判斷下得更快。以下每一條發現都需要
「我改了它，畫面跟著變」這種形式的證據。

## 不可妥協的幾條

**翻譯任何一個字之前，先做零翻譯 round-trip。**
抽出器和插入器接好，什麼都不翻，編一次。每一條字串都必須從編好的 ROM 裡
逐位元組讀回原樣。在這個通過之前，任何翻譯結果都不可信，而且之後每一次出錯
都分不清是「翻譯錯」還是「管線錯」。這個檢查很便宜，而且是整個專案裡 CP 值最高的一個。

**用 ROM 自己的表讀回來驗證。**
不是相信插入器以為自己寫了什麼——要透過 ROM 自己的指標表、自己的字典、自己的字模
去解碼，跟遊戲一樣。一個「安靜地什麼都沒做」的插入器，可以通過任何不這樣做的檢查。

**用目標路徑實際會用的解碼器驗證。**
這條花了真實的時間。CT 的 verifier 用**對白**解碼器讀選單表——而選單根本不用那個解碼器——
於是它讓 294 條選單會畫錯的字串一路開綠燈。如果有兩個子系統在畫字，就需要兩個 verifier。

模擬渲染器也比看畫面**更好**：畫面只顯示游標剛好停在的那一條，模擬涵蓋全部。

**守衛要在出事前寫。**
有些損壞是無聲的——build 綠燈、verifier 綠燈，然後遊戲顯示錯的東西。
每發現一條編碼不變量，就在**產生位元組的地方**加守衛：

- 有結構意義的位元組（分隔符）絕不能出現在編碼後的字串裡
- 目標渲染器不認得的跳脫碼，絕不能被送進那個渲染器讀的表

CT 有個字被配到「低位元組剛好是 `0x09`」的槽位，而 `0x09` 是地名串流的分隔符。
那會把一個地名從中間切成兩半、**後面每一個地名都往後錯一格**，而且全部綠燈。
是事先寫好的守衛在 build 時擋下來的。

**絕不為了技術限制縮短譯文。**
去修那個限制。真的修不了就講出來、問，不要安靜地刪字。
worker 指示裡不可以出現「為了省位元組縮短句子」；唯一的長度規則是畫面寬度。

如果已經因為預算壓力刪過字，**git 找得回來**：對每個區塊取它曾經最長的版本，
現在比那更短、而原文沒變的，就是被刪的而不是被改寫的。

## 動手前要先找到的東西

先回答這些。每一條都需要實驗，不是推論。

**1. 字模。** 幾個字模格、cell 多大、幾 bpp、一個字是連續的還是分塊的？
找法是定位引擎為某個已知字元畫的那塊資料，然後改它。
格數是「這個翻譯能用幾個不重複漢字」的硬上限——在假設放得下之前，
先用原版自己的詞彙曲線推估需求。

**2. 編碼。** 字元碼、換頁跳脫碼、字典或子字串壓縮、控制碼以及哪些帶參數。
**寫一個 parser，讓所有工具都用它。** CT 一度有五份各自重寫的 parse，
每一份都在某個時間點以不同的方式出錯。

**3. 字串的 bank 是從哪裡來的。**
這決定位元組預算能不能整個拆掉。如果位址是（指標表條目）+（指標表所在的 bank），
那麼改那一條指令做重映射，就能把資料搬走，而指標表——可能被 ROM 各處參照、
而且沒有主清單——留在所有人預期的地方。

**4. 是不是有兩套文字系統。**
通常有：對白和選單。要預期它們的**字模**和**解碼器能力**都不一樣。
patch 進其中一套的自訂跳脫碼，在另一套不會動。用觀察來確立各自認得什麼：
CT 的兩位元組換頁碼在選單裡畫出一個字（所以選單認得），
三位元組的自訂跳脫碼則畫出一個延遲加一個雜字（所以不認得）。

**5. 固定寬度的名稱表。**
道具、技能、怪物、角色名常常是用**小字模**畫的固定寬度記錄。
如果那是 8x8，中文就不是選項——8x8 的 CJK 對稍微複雜的字就是不能看，
換任何字型都一樣，十七劃的字沒有 hinting 救得了。
**早點測、早點決定**，不要在草擬完 242 個中文道具名之後才發現。

**6. 壓縮 blob。**
名字和圖形常常是壓縮的。把格式解出來是可行的（在參數空間裡搜出「能解出已知內容」的那組）。
**但寫回去是另一個問題**：一個通過你自己解碼器 round-trip 的壓縮器，
仍然可能產生遊戲的解壓器不吃的串流。
優先考慮**只改 literal 位元組、完全不動 token 串**。

**7. 主腳本表以外的所有文字。**
這個最晚被發現，而且量不小：選單說明列、地名、年代名稱、道具與技能說明、商店文字。
兩種找法：

- **把亂碼反解回日文。** 字模換成中文之後，任何未翻譯的字串都會顯示成特定的錯中文字。
  把那些字經由字模表映射回位元組，再映射回原本的日文，然後在 ROM 裡搜。
  這招把 `準男` 解成 `現代`，直接找到年代名稱表。
- **掃「表的形狀」。** 指標表是一串 16-bit 值，全都指向同一個 bank、位置在表自己的結尾之後、
  而且每個都落在能解成文字的地方。要預期隨機資料會產生大量誤判，內容要用眼睛確認。
  也要預期變體：表可能以 `0xFFFF` 終止，字串也可能根本不是指標表，
  而是用某個分隔位元組串起來的單一串流。

**表的範圍要用它真正使用的終止符去量**，不要用「指標從哪裡開始不像話」——
後者正是 CT 把 46 條的技能表記成 41 條的原因，五條字串就這樣從所有工具的視野裡消失。

## 實際遇過的失敗模式

| 症狀 | 成因 |
|---|---|
| 字數對，但某些字是錯的 | 渲染器不認得的跳脫碼；它吃掉參數，把最後一個位元組當字畫出來 |
| 一個名字從中間裂開，後面全部錯位 | 編碼後的字串裡混進了結構性位元組（分隔符） |
| 開機當機，但內容逐位元組相同 | 重新壓縮的 blob，真正的解壓器不吃 |
| 對白中途當機 | 控制碼 patch 消耗的位元組數跟原版不同 |
| 某個選單顯示完全不相干場景的文字 | 共用視窗，在當前畫面沒東西可畫時不會被清掉 |
| build 和 verify 都綠，畫面是錯的 | 用錯的解碼器驗證 |

## 管線形狀

與遊戲無關，只有常數會變。**把每個遊戲的常數集中在一個模組**，
每一個常數旁邊寫上證明它的反組譯或實驗。

```
extract     ROM -> 純文字區塊，一張表一個檔，用 [nnnn] 分隔
charsetgen  譯文 -> 槽位配置（這一步「就是」在決定編碼）
fontgen     槽位 -> 字模點陣
insert      區塊 -> 編碼、重新打包、改寫指標表
verify      編好的 ROM -> 文字，跟原稿逐條比對
lint        顯示寬度、控制碼原樣保留在原位
```

有兩個工具值得早點做，它們會回本：

- **`consistency`** —— 拿譯文去比對譯者們議定的術語，讓漂移看得見。
- **`trimmed`** —— 走 git 歷史找變短的區塊，讓預算造成的損害可以還原。

## 平行翻譯

一個 worker 配一個檔案地展開。這是可行的——CT 的 5,377 個區塊就是這樣翻完的——
但 worker 之間看不到彼此，所以：

- 一份**具約束力的 glossary**，每個 worker 都讀，是唯一的共享狀態。
- 每個 worker 一份筆記檔記錄它的決定；把**跨檔出現**的術語合併進主表，一次性的留在筆記裡。
- **術語表是預設，不是鐵律。** 專有名詞必須一致；語氣詞要照角色語體——
  同一個詞被兩個角色說，可以正確地有兩種譯法，把它壓平是真實的損失。
- build 要用鎖序列化；worker 絕不可以自己跑完整 build。
- 一致性報告需要詞界規則（在日文裡「換字體系」是可用的詞界），
  否則短的假名詞幾乎全是誤命中。也要注意重複的滑動視窗區塊會灌水。

## 流程

**第一天就裝一個有除錯器的模擬器**（Mesen、bsnes-plus）。
CT 最大的單一浪費，是為了找一份字模而掃遍全 ROM 找壓縮 blob、寫點陣指紋比對器——
而在 VRAM 上傳處下一個中斷點，幾分鐘就有答案。

**在主機上測，不要在腦袋裡測。** 把「載入 ROM + 截圖」寫成腳本，讓看一次 build 很便宜。
注意：**閒置時會暫停的模擬器會給你黑畫面，而那看起來跟當機一模一樣**——
從黑畫面下任何結論之前，先確認模擬器真的在跑（CPU 使用率是最快的判斷）。

**絕不覆蓋使用者既有的 ROM 或存檔。**
複製 build 到裝置時給它一個不同的檔名：模擬器的存檔是用 ROM 檔名當 key，
所以不同的檔名也讓兩個版本的存檔互不干擾。
**用雜湊確認傳輸成功，不要用「沒有報錯」。**
